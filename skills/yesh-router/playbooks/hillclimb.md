# Hillclimb

Use for sustained improvement of one measurable outcome. The user can describe the target without naming this playbook. Use [perf-issue](perf-issue.md) for a bounded performance complaint.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection.

1. **Define the run.** Use [how](../../how/SKILL.md) to establish the execution path and constraints, reusing a valid source-grounded map. Name the realistic workload dimensions that can move the result (data size, history, state, concurrency) and select a case that reproduces the user's complaint; if none does, fix the repro before climbing. Fix one metric, its direction, and a checkable stop predicate that pairs a target with a floor on attempts, so a lucky early win cannot end the run ("at least 50% better than baseline and at least 10 iterations"). Use the user's numbers when given; resolve missing consequential targets or budgets with the user before experiments.
2. **Build, prove, and freeze the harness.** Read [build the lever](../references/principles/build-the-lever.md) and reuse or create a rerunnable harness. Prove its sensitivity: run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. Vet it with the [benchmark checklist](../../benchmark-checklist/SKILL.md) and make it print its error count and a count of work done, so every later keep-or-revert checks "did it error" and "did it happen" for free. Then freeze it: one command emits the metric as the median of N runs. Record the baseline and a green run of the regression gate before any change.
3. **Open the decision log.** Use [show-me-your-work](../../show-me-your-work/SKILL.md). Keep a `decision.tsv` outside the tracked tree, one row per attempt: id, hypothesis, change, before, after, delta, tests, verdict, note. Read it before each attempt.
4. **Ground each hypothesis** in a specific mechanism from step 1 ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in [perf-issue](perf-issue.md) step 2; borrow the order, not that step's stop rule.
5. **Loop, one hypothesis per iteration.**
   - Measure before and after with the frozen harness and run the regression gate.
   - Accept only when the metric moves past noise and the gate stays green. Otherwise revert the experiment's own edits in full. A tweak that "might help" is not kept.
   - When commits are authorized, make one commit per accepted change, staging only the files it changed. Log the row either way.
   - If delegation helps and is authorized, follow the [delegation contract](../references/delegation.md) with the hypothesis, harness, constraints, and acceptance criteria, and review the diff yourself. Independent hypotheses can run in parallel, each in its own worktree ([state-ownership](../references/principles/state-ownership.md)).
6. **Push past the first plateau.** After several rejects in a row, pivot category, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number: revert a win that breaks behavior, and keep a simplification that holds the number.
7. **Stop** when the predicate is met, the budget is spent, or the remaining ideas are marginal. Do not relax the predicate, and do not quit while cheap untried hypotheses remain. Surface a blocker instead of spinning.
8. **Close.** Complete the decision-trail audit. Report metric and target, baseline to final with percent delta, iterations kept versus reverted, each accepted change on one line, the regression result, the `decision.tsv` path, the harness command, and the best untried idea.
